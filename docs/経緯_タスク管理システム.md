# タスク管理システムの経緯と決定

最終更新：2026/08/14
この文書は「なぜこうなっているか」を残すもの。**同じ検討を繰り返さないため**に書いてある。
仕様は `タスクノートの書き方.md`、構成は `リポジトリ構成.md` を見る。

## そもそも何を作っているか

増野さんは6団体（郷野の郷・構想P・STREAM・安全学校・AI改善・個人）を並行運営し、
実行者とPMの二役を日常的に切り替えている。タスクは196件、1日約11件増える。

**AIにタスク管理をさせている理由は自動化ではない。** 増野さんの言葉：

> 私がタスクの状況を報告するとき、今までのセッションでの作業状況やコンテキストを踏まえて、
> 私の報告で不足する状況も推測してタスクの状況を変更し、他のタスクとの関係も気になる点が
> 見つかれば、私に報告しつつ、それでも曖昧な点は、私に確認ができる対話的な機能があることが重要。
> そうでなければ、プログラムで構築したシステムでタスク管理すればいい。

設計の良し悪しは、**この対話が残るかどうか**で判断する。配管の短さはその次。

## 到達点（2026/08/14）

正本を Obsidian Vault から GitHub private リポへ移し、
**対話→タスク更新→ボード生成→配信→iPhone** が2〜4分で一巡する状態になった。

| 層 | 置き場 | 理由 |
|---|---|---|
| タスク（正本） | GitHub `task-hub` | クラウドから直読直書き。履歴・競合解決・採番の一意性を git が担保 |
| 生成物（ボード） | `board/` → さくら | 正本を持たない。毎回生成する。**手編集しない**のが競合回避の要 |
| 知識・資料 | Obsidian Vault | 3端末Sync運用が完成しており壊す理由がない |

移行は全207ファイルの md5 一致で検証済み。Vault 側の `tasks/` は
各団体 `_to_delete/tasks_移行前_20260814/` に退避してある（削除していない。最低1ヶ月残す）。

## 検討して**採らなかった**案（再検討の発動条件つき）

一日かけて比較した結果。同じ議論を繰り返さないために、却下理由と「いつなら復活するか」を残す。

| 案 | 却下理由 | 発動条件 |
|---|---|---|
| **常駐Macでlaunchd自動push** | **静かに死ぬ**（スリープ・OS更新・plist外れを誰も検知できない）。部品5個 | なし。方式として採らない |
| **PATを埋めた更新ボタン** | 有効期限366日のトークンが無告知で壊れる。非技術者運用に最も向かない部品 | なし |
| **Cloudflare Worker仲介** | 部品と保守主体が増える。環境が意図して塞いだ経路の迂回にあたる | なし |
| **さくらスタンダードのcronでpull型** | 書き込み工程に効かない。cron粒度5〜10分で即時性もない | **国外IPフィルタを戻す決断をしたとき**（引き込み型にすればFTPS受け入れが不要になる） |
| **Cloudflare Pages + Zero Trust** | 動作中の配信を別ベンダーへ載せ替えるだけ。筋は良いが今は動機がない | **外部の人にボードを見せる必要が出てBasic認証のID/PW共有が破綻したとき**（メールOTPで人単位に配れる） |
| **DBトリガー構成（Supabase等）** | 正本の二重化。md 196件という規模に過剰 | なし |
| **Routines（リポ紐付き定期実行）** | @claude と Actions schedule で足りる。管理画面が増える | 上記で回らないと分かったとき |

## 実測で分かった制約（推測ではなく実際に踏んだもの）

- **AIの実行環境は HTTPS(443) 以外の外向き通信ができない。** FTP/FTPS直接アップロードは不可能。
  だからさくらへの配信は GitHub Actions が担当する
- **Cowork からこのリポには push できない**（git proxy が 403）。**clone は通るので誤認しやすい**。
  Cowork の UI にリポジトリをソース追加する手段は見当たらなかった。GitHub REST API も同じく403
- **Code タブのローカル環境なら main へ直 push できる**（増野さん自身の git 認証を使い proxy を経由しない）。
  クラウド環境は `claude/` ブランチ＋PR になる可能性があり**未検証**（iPhone から使うときに要確認）
- さくらへの配信が通らなかった真因は **さくらの「国外IPアドレスフィルタ」**。
  有効だと Actions（米国）からのFTPが `PASS` 直後に無言で切断され `curl exit 56` になる
- macOS標準の bash 3.2 は**変数名の直後に全角文字が来ると名前の切れ目を誤認する**。
  シェルスクリプトでは変数を必ず `${...}` で囲む
- `git pull --rebase` は未コミットの変更があると止まる。AIが編集した直後が通常状態なので
  **`--autostash` が必須**

## 設計上の教訓

- **表示から何かを外すときは「では、どこに残るのか」を実データで確認する。**
  `waiting` を期限アラートから外したとき、「団体別セクションに残るはず」という前提が崩れていて、
  確認していなければタスクが静かに消えていた（→ `👥 待ち` 節を新設して解決）。
  **後日の実測で、6件中2件は待ち節にしか出ていないと確認**（→「優先課題」の節）
- **生成物を差分で検証する仕組みを持つなら、入力順に依存する箇所を先に潰す。**
  タスクの読み込み順で同着タスクの並びが変わっていたため、`id` でソートを確定させた
- 移行の検証は**ローカルの作業コピーを信じず、GitHubから clone し直して原本と md5 照合**する
- ログを共有してもらうときは「`USER`/`PASS` を含む行を消す」と**具体的に**伝える
  （`curl -v` の出力にパスワードが平文で出て、変更する事故があった）

## セッションの使い分け

| | 使うもの | 理由 |
|---|---|---|
| **日常のタスク管理** | **Code タブ・ローカル環境**（このリポ） | 対話しながら直接編集・検証・push できる |
| **このシステムの改良** | 同上 | 対象（`scripts/` `tasks/`）がリポの中にある。生成して差分を見るまでが一続き |
| 調査・設計判断 | Cowork | 複数のサブエージェントを並行させて比較検討する類 |
| 文書作成・Drive連携・デザイン | Cowork | フォルダ連携とプロジェクト機能が効く領域 |

増野さんの整理：**Coworkで業務を進め、それが定型化したら効率化するシステムを開発し、
その段階でCodeへ移す。** この流れがClaudeの使い方として自然。

## 優先課題：タスクの持ち方と親子構造の整理（2026/08/14 提起）

**下の「次にやること」より先に、これを落ち着いて整理する。** 個々の表示バグとして塞ぐと、
同じ穴が別の場所に開く。急いで対症療法を当てないこと。

### 何が起きていたか（実データで確認済み）

`waiting` を期限アラートから外した直後、6件の待ちタスクがどこに出ているかを HTML で数えた。

| ID | 団体別ボード | 出方 |
|---|---|---|
| KOSO-028 / STRM-007 / ANZN-008 | ○ | 親の行の下に子行（`class="child"`）として |
| GONO-131 | ○ | 「期限の近い順」8件の枠に自力で入っている |
| **GONO-130 / GONO-106** | **×** | **`👥 待ち` 節にしか無い** |

`👥 待ち` 節を作っていなければ、この2件はボードから完全に消えていた。
「団体別セクションに残るはず」という前提は、実際に崩れていた。

### なぜ消えるのか

団体別ボードの「期限の近い順」は **`parent` を持つタスクを除外**したうえで**上位8件で打ち切る**。
子タスクは**親の行にぶら下がる形でしか表示されない**。ここから2通りの消え方が生まれる。

- **親が枠外だと子も出ない**（連鎖）。GONO-130 の親 GONO-009 は due 8/31 で、
  郷野の郷120件の8件枠（8/20〜8/31 で埋まる）に入らない
- **親なしでも枠から溢れれば数字に吸収される**。GONO-106（due 9/10）は
  「期限が先のもの 63件」に数えられるだけで、ID は出ない

**件数の多い団体ほど受け皿として機能しない。** 郷野の郷は120件中IDが見えるのは9件。
構想P37件・STREAM11件・安全学校12件で見えていたのは、たまたま親が枠に入る規模だっただけ。
当面の実質的な受け皿は期限アラート（14日以内）と `👥 待ち` 節であり、
**「団体別ボードを見れば全部ある」と考えてはいけない。**

### 整理したい論点

1. 表示上限8件の是非。団体の件数に応じて変えるのか、そもそも件数で切るのが正しいのか
2. 親が枠外のときに子をどう扱うか（子を独立に出す／子がいる親を引き上げる）
3. `parent` の使い分け。企画の細目・手続きの工程・単なる関連が、今は同じ `parent` で表現されている
4. `tasks/` フラット196件をどう持つか。`archive/` の月次運用が始まると母数の前提も変わる
5. **「生きているタスクは、ボードのどこかに必ず1回は出る」を設計原則として明文化するか**

### 進め方

増野さんの原則どおり**感覚でなく分布を数えてから決める**。
まず実データで、`parent` を持つタスクの割合・親子の深さ・団体別の件数分布を出す。
その数字を見てから、上の1〜5を決める。

## 検討課題：期間内に毎日少しずつ進めるタスク（2026/08/15 提起）

AIW-011（タスクボードのUI改良・8/31まで毎日少しずつ）で初めて出てきた形。
**いまの語彙では表現できていない。** 当面は `status: doing` のまま置き、
やる日に `today` を付け直す運用で試すが、これは仮置き。

既存のどれとも違う：

- `due` は「その日までに終える」だが、この種のタスクは**終わりの日はあるが、毎日が本番**
- `this_week`（今週やる意思の枠）は週単位。日々の継続を表せない
- `config/recurring/<接頭辞>.md` の定期タスク（草刈りなど）は**間隔をあけて繰り返す**もので、
  「連続した期間、毎日」とは別物

### 論点

1. **完了の単位**。1日分の完了と、タスク全体の完了をどう区別するか
2. **毎日の `today` を人が付け直すのか、期間中は自動で出すのか**（`daily: 2026/08/15〜2026/08/31` のような持ち方）
3. **負荷（7枚制限）にどう数えるか。** 毎日1枠を占め続けるのか、軽く数えるのか
4. **やらなかった日をどう扱うか。** 未達を責める作りにすると続かない
5. 進捗の見せ方。「8/31まであと N日、うち実施 M日」のような形が要るか

### 進め方

**AIW-011 そのものを実験台にする。** 8/31まで実際に運用してみて、
何に困ったかを AIW-011 の「改良したいことの置き場」に書き溜め、
月末に上の1〜5を決める。**先に仕組みを作らない。**
